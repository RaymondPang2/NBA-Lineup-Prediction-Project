# Public deployment on Render (synthetic-data demo)

**Status:** ready to deploy. `render.yaml`, the Docker image and the start-up seeding are built and tested locally under Render's free-plan limits. The site is **not live yet**: creating it needs the owner to authorize Render (steps at the end).

[![Deploy to Render](https://render.com/images/deploy-to-render-button.svg)](https://render.com/deploy?repo=https://github.com/RaymondPang2/NBA-Lineup-Prediction-Project)

## What gets deployed, and why it uses synthetic data

NBA.com's Terms of Use (section 9, "NBA Statistics") allow its statistics only "for legitimate news reporting or private, non-commercial purposes". They forbid their use "in connection with any website, product, or service that features a database … of comprehensive, regularly updated statistics" without the NBA's consent. A public website isn't private, so **the public site doesn't show the real data**.

Instead it runs a **synthetic league**: 30 fictional teams and 390 fictional players over two seasons of 1,230 games each, generated by `src/nba_lineups/demo/league.py`.

**It goes through the real pipeline.** The synthetic league answers the same four endpoints the real ingester calls, so these all run unchanged:
- payload validation;
- the ETL and its one-transaction load;
- all 16 data-quality checks (zero failures, zero warnings);
- the SQL rating views;
- the frozen linear-regression model;
- the API and the dashboard.

**Labelling:**
- Every page shows a non-dismissable "Synthetic demo data" banner, and the footer says the data is fictional.
- Seasons are labelled "synthetic", every prediction carries a synthetic-data note, and `/health` reports `"mode": "demo"`.
- The Model page states that its results are **real**: they were measured on actual NBA seasons during private development.
- No NBA team names, cities, nicknames, team IDs or logos are used (a test enforces this).
- The image can't contain real data: `.dockerignore` excludes `data/` and the API fixtures, and a test checks it.

The real-data version, with every NBA lineup since 2018-19, 2026-27 and the daily refresh, stays on the owner's machine.

## Architecture

```
GitHub (main) ──push──► Render ──builds──► Docker image (Dockerfile)
                                            ├─ stage 1: Node 22 builds the React dashboard (VITE_DEMO_MODE=1, API on same origin)
                                            └─ stage 2: Python 3.12 + FastAPI + frozen model (models/final, hash-verified)
Render web service "lineup-lab" (free) ── private network ──► Render Postgres "lineup-lab-db" (free, not internet-reachable)
   https://<name>.onrender.com/          the dashboard (single-page app; client routes fall back to index.html)
   https://<name>.onrender.com/api/v1/…  the read-only API        /docs  OpenAPI UI        /health  readiness
```

**Why one service rather than a static site plus an API service:**
- In a Blueprint, `fromService … property: host` gives another service's *private-network* hostname, not its public URL.
- Free web services can't receive private-network traffic.
- So a separate static site couldn't be wired to the API's public URL without a manual step.

Serving the built dashboard from the API (`NBA_API_STATIC_DIR`, `api/main.py:mount_dashboard`) gives one HTTPS URL, same-origin requests (no CORS) and zero manual configuration. Hashed assets get a one-year cache; HTML gets `no-cache`.

## Start-up and database initialization

`CMD` starts uvicorn immediately and runs `python -m nba_lineups.demo.seed` in the background:

1. **Wait:** for PostgreSQL, for up to 2 minutes.
2. **Check:** if every demo season is already loaded, do nothing. This is the normal case for restarts and wake-ups.
3. **Load what's missing:** otherwise, build the missing seasons through the real pipeline, one transaction per season, under an advisory lock. A start interrupted mid-build resumes on the next start; this was tested by restarting the container half-way.
4. **Never touch real data:** it refuses any database that contains a non-demo season.
5. **Report readiness:** `/health` answers **503 `"seeding"`** until every season is loaded, and **200** once ready. Render only routes traffic to a healthy instance, and restarts one whose seed failed.

## Measured resource use

Measured locally with Docker limited to the free plan (512 MB RAM, 0.1 CPU):

| | |
|---|---|
| Peak memory, seed and server together | **234 MB** (of 512 MB) |
| First start on an empty database | about 3–3.5 minutes to healthy (the seed takes about 85–90 s at 0.1 CPU) |
| Later starts or wake from sleep | about 60 s to healthy (importing pandas and scikit-learn, loading the model, at 0.1 CPU) |
| Database size | 12 MB (2 synthetic seasons, about 2,400 lineups); the free plan allows 1 GB |
| Image size | about 930 MB (Python data stack) |

## Cost and plan choice

Both resources are on Render's **free** plans; nothing paid is provisioned. The owner's approval is needed to change any plan.

| Resource | Plan | Cost | Limits to know |
|---|---|---|---|
| Web service `lineup-lab` | free | $0 | Sleeps after 15 idle minutes, so the first visit after that waits about 1–2 minutes. 750 free instance hours a month per workspace |
| Postgres `lineup-lab-db` | free | $0 | **Expires 30 days after creation**, then a 14-day grace period before deletion. 1 GB, no backups, one free database per workspace |

**When the free database expires**, the owner chooses one of two options:
- **Stay free:** delete `lineup-lab-db` in the Render dashboard, then *Blueprints → lineup-lab → Manual Sync*, which recreates an empty free database. Restart the web service. The demo seeds itself in about 3 minutes, and no data is lost because the data is generated. Repeat every 30 days.
- **Upgrade (needs approval):** change the database to the smallest paid instance. Optionally move the web service to a paid instance so it doesn't sleep. Check current prices on render.com/pricing before deciding. Third-party 2026 summaries quote about $6–7 a month each, but that is unverified here.

## Automatic deployments

`autoDeployTrigger: commit` on branch `main`: every push to `main` rebuilds and redeploys the service through the Blueprint. The database and its data persist across deploys.

## Owner steps (account authorization only)

1. Click **Deploy to Render** above, or open <https://dashboard.render.com/blueprints>, choose **New Blueprint Instance** and select the `NBA-Lineup-Prediction-Project` repository.
2. Sign in to Render (GitHub sign-in is easiest) and allow Render's GitHub app to access that repository.
3. Render shows the Blueprint: **lineup-lab** (web, Free) and **lineup-lab-db** (Postgres, Free). Keep the default names, check that both say **Free**, and click **Apply** (or **Deploy Blueprint**). No payment method or environment variables are needed.
4. Wait for the first deploy, about 5–10 minutes: Docker build, then about 3 minutes of seeding. The service turns **Live** when `/health` returns 200.
5. Copy the service URL (`https://lineup-lab….onrender.com`) and send it back, so the live site can be verified and the README updated.

Checks once live:
- `/health` returns `"status": "ok", "mode": "demo"`;
- `/` shows the synthetic-data banner;
- `/rankings`, `/predict` and `/model` load;
- `/docs` shows the API.
